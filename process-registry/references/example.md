# Worked example: weekly missed-call report

An invented process, filled in end to end. Use it to judge how much detail each file needs and where the line sits between the definition of done and the test.

## The request

"Every Monday, pull last week's missed calls per location, build a summary table, draft the note to location managers, and send it."

## Stages

Applying the stage test and the gate test from SKILL.md:

- **Collect** the call data. It is the source data everything else trusts, so it gets a gate (gate test 3).
- **Build the table** and **draft the note**. Neither needs the other, so they share a step. No gate: nothing leaves yet, and the next gate covers them.
- **Assemble** the final email from both. This is the thing about to be sent, so it gets a gate (gate test 1). The check happens before the send.
- **Send**. No gate, because a check after sending cannot stop a bad email. The owner said a person approves the send, so it waits for a human yes.

```bash
python scripts/scaffold.py runbook --registry registry --qa registry-qa \
  --id missed-call-report \
  --description "Builds and sends the weekly missed-call report per location. Use when the Monday report is due or someone asks for last week's missed calls." \
  --stages "collect, build-table | draft-note, assemble, send" \
  --gates "collect, assemble" --human-gate send
```

## registry/.../01-collect/STAGE.md

```markdown
# 01-collect

## Purpose

Get last week's call records into one clean file that the later stages can trust.

## Inputs

| Source | Location | Why |
|---|---|---|
| Phone system export | The call log export for the report week | The raw calls |
| Location list | `references/locations.csv` in this stage | Which locations to include |

Read only what is listed here.

## Process

1. Set the report week: the last full Monday-to-Sunday week before the run date.
2. Export every inbound call in that week for every location in the location list.
3. Keep these fields per call: location, start time, answered or missed, wait time in seconds.
4. Drop test calls and internal extensions. Record how many rows were dropped and why.
5. Save the calls and a short notes file.

## Output

Write to `<run folder>/01-collect/output/`. `deliverable.md` says what must be in it.
```

## registry/.../01-collect/deliverable.md

```markdown
# Deliverable: 01-collect

This is the definition of done for the maker. It says what good looks like.
It does not say how the work is tested.

## Hand in

- `calls.csv`
- `notes.md`

## Format

`calls.csv` has one row per inbound call with columns: location, start_time, outcome, wait_seconds. `outcome` is `answered` or `missed`.
`notes.md` states the report week, the row count, and what was dropped and why.

## Must be true

- Every inbound call in the report week, for every location in the list, appears exactly once.
- No call from outside the report week is included.
- A reader can tell from `notes.md` which week this is and what was left out.

## Out of scope

- Totals, rates or any analysis. That is the next step.
```

Note what this file does: it states the outcome fully, so a maker knows exactly what to aim for. It says nothing about how completeness will be checked.

## registry/.../01.1-qa/GATE.md

Generated by the scaffolder and left alone. It says the QA agent grades `01-collect/output/`, that criteria are at the same path in `registry-qa`, and what happens on pass and fix.

## registry-qa/runbooks/missed-call-report/01.1-qa/qa.md

```markdown
# QA criteria: missed-call-report / 01.1-qa

Grades the output of `01-collect`. Makers never see this file.

## Scripted checks

- `calls.csv` and `notes.md` exist.
- Columns are exactly: location, start_time, outcome, wait_seconds.
- `outcome` holds only `answered` or `missed`.
- Every `start_time` falls inside the report week stated in `notes.md`.
- Every location in the location list appears, or `notes.md` says why it has no calls.
- Row count is within 1% of the phone system's own inbound total for the week, after the drops listed in `notes.md`.
- No duplicate rows on location + start_time.

## Judgment checks

- The reasons for dropped rows are plausible. Fail if a whole location or a whole day was dropped without a reason.

## Golden set

`golden/good-full-week/` is a correct deliverable for a sample week. `golden/bad-missing-sunday/` is a known-bad one where the export stopped a day early; its `why.md` says so. The gate must pass the first and fail the second before it is used on real work. Use them to calibrate, not to diff against.

## Sources a fix note may cite

- The phone system export and its own weekly total.
- The location list.
- `deliverable.md`.

## Passing

Every scripted check and the judgment check pass.
```

The 1% tolerance and the duplicate key are test details. They appear here and nowhere in the main registry.

## A fix note for this gate

```
QA REVIEW: FIX 1/3
Gate: 01.1-qa  Run: 2026-11-16-a
Fix:
1. [calls.csv] no rows for Sunday of the report week. Evidence: the phone system export shows inbound calls on that date for all locations.
2. [notes.md] the dropped-rows count is given with no reason. Evidence: deliverable.md, "what was dropped and why".
Keep (verified correct, do not change):
- Column names and order
- Rows for Monday to Saturday
- The report week stated in notes.md
```

Each item points at evidence the maker can open. Neither mentions the tolerance, the duplicate check or the golden folders.

## How the run goes

1. `01-collect` runs, hands in, and passes `01.1-qa` on the second try.
2. `02a-build-table` and `02b-draft-note` start together, each as its own task.
3. Both finish. `03-assemble` builds the final email and passes `03.1-qa`.
4. `04-send` is in `human_gate`, so the orchestrator asks the named person and waits. They approve an email that has already been checked.
5. After the yes, `04-send` runs. The run is done.
